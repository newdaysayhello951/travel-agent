# 架构决策记录（ADR）

记录本项目在改造过程中做出的关键取舍：**决策 / 背景 / 权衡 / 结论**。面试时这些条目可以直接作为"为什么这么设计"的回答骨架。

---

## ADR-001 用 LangGraph 图编排，而不是手写 if-else

**背景**：客服消息需要"判断意图 → 分派处理 → 出口审查 → 汇总"，朴素写法是一串条件分支加局部变量传递。

**权衡**：
- 手写分支：上手快，但流程写死在代码里，状态靠参数传递，没有检查点，无法支持多轮记忆与断点恢复；
- 图编排：引入一层抽象与学习成本，但流程与状态解耦、边可声明式表达、检查点可复用。

**结论**：采用 LangGraph。加一个 Agent 只需加节点和边，不用改已有节点。

---

## ADR-002 `sub_results` 不加 reducer

**背景**：`messages` 用 `add_messages` 追加合并；`sub_results` 作为多个 Agent 的产出容器，直觉上也该加合并 reducer。

**权衡**：加 reducer 能防并行写互相覆盖；但 reducer 会把 `initial_state` 传入的空字典与**检查点里的旧值**合并，导致**上一轮的中间结果串进本轮**。

**结论**：**不加**。当前是串行流水线，保持默认覆盖语义可保证每轮干净；节点自行合并已有结果。等引入并行节点时，再配合显式重置或 `RemoveMessage` 一起改。已写测试固化该行为。

## ADR-003 检索用本地词法匹配，不用向量数据库

**背景**：RAG 需要一个检索器。

**权衡**：
- 向量检索：能匹配同义词、语义相近的表达；但需要 Embedding 模型与向量库，增加依赖与成本，且对**精确匹配**（订单号、编码）反而更弱；
- 词法匹配：零外部依赖即可跑通，精确匹配强；但同义词召回差、缺少 IDF 权重。

**结论**：演示与客服短文本场景用**词法匹配**（中文相邻两字切分 + 词元重合度）。分块改为**段落感知**，避免把句子拦腰切断。升级路径清晰：替换 `LongTermMemory.search()` 即可，上层不动。

## ADR-004 合规审查做两阶段，并采用 fail-closed

**背景**：金融客服出现"保证收益"这类话术是监管风险，需要在出口拦截。

**权衡**：
- 只用规则：毫秒级、零成本、可解释，但只能匹配已知模式，换个说法就绕过；
- 只用 LLM：能覆盖未知语义，但慢、贵、结果不确定。

**结论**：**两阶段**——规则先跑（不通过就短路，不花模型的钱），通过后再做 LLM 深度审查（兜住规则表漏掉的语义）。审查结果**解析失败时判定为不通过**（fail-closed）：安全场景下"不确定"必须当作"不安全"。

## ADR-005 结构化输出必须显式指定 `method="function_calling"`

**背景**：路由原先靠"自由文本 + 白名单兜底"，改造成 Pydantic 结构化输出。

**权衡 / 事实**：`with_structured_output()` 的默认实现走 `response_format`(json_schema)，而实测所在网关**以 400 拒绝**（要求 messages 里出现 "json" 字样）；只有 `function_calling` 可用。

**结论**：显式传 `method="function_calling"`，并做成配置项。**这个坑单测与静态检查都发现不了**——第一次真实端到端运行时，业务是成功的，只有日志里躺着一行"结构化路由调用失败，回退到文本解析"，说明新写的路径从未真正生效。

## ADR-006 并发闸门按调用方分桶，而不是全局串行

**背景**：一次问答要调用 5 次模型，本机演示要避免把上游网关的额度与频率打爆。

**权衡**：
- 全局 `Semaphore(1)`：实现最简单，但把**整个服务**的吞吐锁成串行，并发上来后排队请求必然超时；
- 按调用方分桶：单调用方仍受保护，不同调用方互不拖累。

**结论**：按调用方分桶。已用测试断言"不同调用方并行、同一调用方串行"。

---

## ADR-007 token 计量用代理包装，而不是逐点埋点

**背景**：需要统计模型调用成本。

**权衡**：
- 在 5 个调用点分别埋点：直接，但**新增调用点就会漏统计**，且侵入业务代码；
- 代理包装模型客户端：一处实现全覆盖，Agent 代码零改动，但多一层间接。

**结论**：用 `MeteredLLM` 代理，覆盖 `ainvoke` 与 `with_structured_output`，其余属性透传。

## ADR-008 日志初始化放在 lifespan，而不是模块导入时

**背景**：应用侧 `logger.info(...)` 长期不输出。

**事实**：uvicorn **在导入 app 之后**才执行自己的 `dictConfig`，会覆盖模块级添加的 handler。第一次把初始化放在模块级，实测仍然不可见。

**结论**：放在 `lifespan`（uvicorn 配置之后执行）。

---

## ADR-009 上下文窗口按偶数条裁剪

**背景**：路由 prompt 会把历史全量喂给模型，token 成本随轮数线性增长，最终撞上上下文上限。

**权衡**：裁剪条数随意取值会破坏"提问 + 回答"的配对，留下孤立回答。

**结论**：路由 prompt 只取窗口内最近消息；出口节点用 `RemoveMessage` **按偶数条**从最前面移除，保证剩余历史仍是成对结构。上限由 `MAX_CONTEXT_MESSAGES` 控制。

---

## ADR-010 测试用假模型，不调用真实模型

**背景**：需要一套可重复、不烧额度的回归测试。

**权衡**：真实模型能验证真实行为差异（如 ADR-005 的网关差异），但无法离线、不可重复、消耗配额；假模型快且稳定，但**与真实模型的差异无法覆盖**。

**结论**：两者都要——**pytest 用假模型做回归**，**关键改动再用真实调用做验收**。ADR-005 正是"只有真实调用才能发现"的例子。
