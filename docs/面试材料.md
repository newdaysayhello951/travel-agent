# 面试材料

面向"把这个项目写进简历"的整理：一句话介绍、亮点、高频追问的标准答法，以及**必须主动说出的能力边界**。

---

## 一、一句话介绍（约 30 秒）

> "这是一个基于 **LangGraph 编排的多 Agent 客服后端**。用户消息进来后由主管节点判断意图，路由到**知识问答（RAG）**或**工单处理**分支，产出结果必须经过**两阶段合规审查**；审查不通过时会让模型**自动整改并复审**，最后汇总返回。技术栈是 **FastAPI + LangGraph + LangChain + RAG**，工单与多轮对话都落 SQLite，工具层走 MCP 协议。"

**结构**：做什么 → 怎么流转 → 用什么做的。

---

## 二、三条可写的核心工作

1. **多 Agent 图编排**：基于 `StateGraph` 设计"路由 → 执行 → 合规审查 →（不通过则整改复审）→ 汇总"的流水线，用**条件边**实现意图分流，用**共享状态 + 检查点**实现跨轮记忆，并用**回边**把合规审查从"一次性闸门"升级为 **evaluator-optimizer** 闭环。
2. **RAG 四段式问答**：实现"Query 改写 → 检索 → 重排 → 生成"链路；检索层用**中英词法匹配**（中文 bigram + 词元重合度）做到零外部依赖；**无检索结果时不调用模型**，从机制上消除幻觉。
3. **两阶段合规审查 + 工程化**：规则引擎快筛（敏感词表 + PII 正则 + 脱敏）配合 LLM 深度审查，判定采用 **fail-closed**；另接入 SQLite 持久化（工单 / 图检查点 / 知识库索引）、API Key 鉴权与按调用方限流、MCP 工具层与 OpenTelemetry 可观测。

## 三、高频追问与标准答法

| 追问 | 答法要点 |
|---|---|
| **这是多智能体还是工作流？** | **诚实定性**：属于 routing workflow + evaluator-optimizer。流程与边由代码预定义，没有并行、没有 Agent 间协商；**只有合规环节存在真实循环**。要说清它具备什么（职责单一、共享状态协作、条件路由、强制出口审查、自动整改闭环），以及要变成自主 agentic 还缺什么（自主工具调用循环、动态任务拆解、反思策略）。 |
| **为什么不加向量检索？** | 零依赖跑通；客服场景有大量**精确匹配**（订单号）需求，那是向量检索的弱项；升级路径清晰——替换 `search()` 实现即可。短板是同义词召回差。 |
| **为什么 `sub_results` 不加 reducer？** | 加了会让 `initial_state` 的空值与**检查点旧值**合并，**上一轮结果串进本轮**。当前串行流水线保持覆盖语义更安全，节点自行合并；引入并行时再改。**已写测试固化。** |
| **上下文会不会无限增长？** | 会，所以做了两层：路由 prompt 只取窗口内最近消息；出口节点用 `RemoveMessage` **按偶数条**裁剪检查点，保证剩余历史仍是问答成对。 |
| **模型输出不可信怎么办？** | 三处防御：路由用**结构化输出**（枚举约束）；工单指令解析失败落到"没听懂"分支而不是谎称功能不支持；合规审查**解析失败一律判不通过**。 |
| **并发怎么处理？** | 原先全局 `Semaphore(1)` 把服务锁成串行，已改为**按调用方分桶**：单调用方仍受限（保护上游额度），不同调用方互不拖累。测试断言了"不同调用方并行、同一调用方串行"。 |
| **怎么知道慢在哪一步？** | OpenTelemetry 装饰器给每个 Agent 方法建 span；`/api/metrics` 暴露 per-agent 调用数/耗时/错误率与 **token 用量**；`/api/chat/stream` 用 SSE 逐节点推送进度。 |
| **这个项目你最有收获的一次排查？** | 结构化路由在真实链路上**一直在静默回退**：业务成功、日志只有一行 warning。根因是 `with_structured_output()` 默认走 `response_format`，被网关 400 拒绝，必须显式 `method="function_calling"`。**假模型和静态检查都发现不了。** |

## 四、必须主动说出的能力边界

> "它现在是**本机可运行、可测试**的形态，离生产还有距离，我知道边界在哪："

| 维度 | 缺口 |
|---|---|
| 协议 | 只实现了 MCP 的 **tools 子集** + 一个 HTTP JSON-RPC 入口，没有传输层、没有 `initialize` 握手与能力协商 |
| 检索 | 词法匹配，**不是真实向量检索**；同义词召回差 |
| 安全 | 只有静态 API Key，没有用户体系、密钥轮换、审计日志 |
| 扩展性 | 限流与并发闸门是**进程内**实现，多实例需换 Redis；短期记忆的 Redis 路径当前是降级到内存 |
| 数据 | 知识库是三篇演示文档；`order_query` 等工具仍是演示数据 |
| 工程 | HTTP 层（401/429/`/mcp`/SSE）缺自动化测试；无覆盖率统计 |
| 智能 | 整改只做一次全量重写，**不校验整改后的事实是否与原文一致** |
