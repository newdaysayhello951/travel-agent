# 补齐HTTP层测试并统一限流

改造计划阶段 7 的最后一块：把 HTTP 层纳入自动化测试。这也是此前两轮排查反复印证的最大技术债——手工 curl 验证既不可靠（曾制造幽灵缺陷）、也漏掉了真实缺口。

## 修改内容

### 1. 新增 `tests/test_api.py`（HTTP 层测试）

用 `httpx.ASGITransport` 直接驱动 ASGI 应用：**不触发 lifespan**，因此不会编译图、也不会调用真实模型。覆盖：

- 公开端点 `/health` 免鉴权；
- 鉴权：无密钥 401（含 `WWW-Authenticate`）、错误密钥 401、受保护端点（`/api/tools`、`/api/metrics`、`/mcp`、`/api/chat/stream`）均需密钥；
- **携带正确密钥的请求越过鉴权**（落入"图未就绪"的 503 分支，证明鉴权确实放行）；
- 限流：令牌耗尽后 429 且带 `Retry-After`、不同密钥配额互相隔离；
- 输入侧检查：提示注入返回 400；
- MCP 入口：`ping`、`tools/list`、未知方法 `-32601`、以及 `/api/tools/call` 走通工单工具。

### 2. 修复一个真实的限流缺口

写测试时发现：**限流原先只加在聊天接口上**。`/api/tools`、`/api/metrics`、`/api/history`、`/mcp`、`/api/tools/call` 这些**受保护接口完全没有限流**——而 `/api/tools/call` 会真正执行工具（含数据库写入），属于可被刷的入口。

修法：**把限流下沉到鉴权依赖 `require_api_key` 里**。这样"需要鉴权的接口"与"受限流的接口"自动对齐，不会因为新增接口而漏配。本机演示模式（未配置密钥）走 `ANONYMOUS` 分桶，同样受限流保护。

### 3. 让响应头反映真实的剩余配额

`api/main.py` 原先自己 `new` 了一个限流器用于读 `remaining()`，与鉴权依赖用的是**两个不同实例**——响应头里显示的"剩余配额"其实是假的（永远是满额）。现改为共用 `get_limiter()` 返回的进程级实例。

## 修改原因

用户要求按七阶段计划改造项目。阶段 7 的收尾项就是补上 HTTP 层测试。此前两轮已经用事实说明手工验证的代价：一次因请求体编码把中文变成 `?`，导致连续两轮去怀疑应用代码；而同一次手工验证也**没有发现"限流只覆盖聊天接口"这个真实缺口**——写自动化测试时它立刻暴露了。

## 验证结果

- **`pytest` 全量通过**（含新增的 HTTP 层用例）。
- 全部模块导入成功；`compileall` 通过。
- 新增测试**不触发 lifespan、不调用真实模型**，可离线重复运行。

## 未解决的问题

### 测试设计与实现上的自我修正（记录以便复用）

1. **限流配额把普通用例"饿死"**：最初把 `RATE_LIMIT_BURST` 设为 1，而多个用例复用同一个密钥，于是第一个用例就把令牌耗尽、后续用例全变成 429。改为调高配额，**429 用例自己驱动限流器耗尽令牌**，从而不依赖配置值、结果确定。
2. **表不存在**：`ASGITransport` 不触发 lifespan，而建表动作在 lifespan 里，导致工具调用报错。现由夹具显式调用 `database.create_all()`（等价于真实启动时的动作）。
3. 编辑过程中我在 `remaining()` 里写入了一段语法合法但逻辑错误的表达式（`now - bucket.elapsed if False else ...`），已修正——**这类"能跑但语义错"的代码是最难自查的**，值得警惕。

### 仍未完成
