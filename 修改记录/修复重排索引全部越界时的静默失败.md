# 修复重排索引全部越界时的静默失败

本文件对应一次**部分成功**的排查：修掉了一个真实缺陷，但**线上症状依旧存在，根因尚未定位**。

## 背景

阶段 6-B 的 SSE 真实验证中，知识问答返回了兜底话术"知识库中暂未找到与您问题相关的信息"。对照验证却显示知识库正常：服务启动日志为 `{'rebuilt': False, 'documents': 3, 'sources': 3}`，直接用同一索引检索也能命中 `refund_policy.md`（score 0.636）。两者矛盾，需要定位。

## 排查过程与证据

### 1. 用真实模型单独跑 RAG 四步 —— 全部正常

```
索引文档数 = 3
1) 改写结果 = '退款申请时效 购买后几天内'
2) 检索命中 = 2 ['refund_policy.md', 'account_guide.md']
3) 重排结果 = 1 ['refund_policy.md']
4) 生成回答 = 用户在购买后**7天内**可申请无理由退款。…（并带来源与风险提示）
```

结论：四段式本身没有问题，问题出在"接进图之后"的运行路径上。

### 2. 代码审查发现一个真实的静默失败

`KnowledgeRAGAgent.rerank_documents()` 的兜底只在**抛出异常**时生效：

```python
try:
    indices = [int(i.strip()) for i in response.content.split(",")]
    reranked = [documents[i] for i in indices if 0 <= i < len(documents)]   # 全部越界 → []
except (ValueError, IndexError):
    reranked = documents[:top_k]        # ← 不抛异常就不会走到这里
return list({doc["id"]: doc for doc in reranked}.values())[:top_k]          # → 返回空列表
```

**模型给出的索引如果全部越界，过滤结果是空列表且不抛异常**，兜底分支不触发，空结果被下游当成"没有检索到资料"——这正是我此前讲课时提过的**静默失败**。

## 修改内容

在 `rerank_documents()` 中显式兜底：过滤后为空则回退到检索顺序，并记录一条警告日志（便于下次定位）。

```python
if not reranked:
    logger.warning("重排返回的索引全部无效，回退到检索顺序: %r", response.content[:80])
    reranked = documents[:top_k]
```

并新增 `tests/test_rag.py`（7 个用例）覆盖：合法索引、重复索引去重、输出无法解析、**全部越界**（回归用例）、负数索引、空输入、以及"无检索结果时不调用模型"。

## 修改原因

这是排查"知识库检索返回空"时发现的独立缺陷。即使它不是本次线上症状的根因，也应当修掉——否则同样的静默失败会在其他场景复现。

## 验证结果

- **`pytest`：87 passed**（新增 7 例）。其中"全部越界"与"负数索引"两个用例在修复前会失败：前者返回空列表，后者在 Python 里 `-1` 是合法下标、会取到**最后一篇**文档（同样是静默错误）。
- 全部模块导入成功；`compileall` 通过。

## 未解决的问题

### ⚠️ 线上症状依旧存在，根因未定位

修复后重新做**真实端到端请求**（`POST /api/chat`，真实模型）：

```
intent = knowledge_rag
compliance = True
response = 抱歉，知识库中暂未找到与您问题相关的信息。建议您联系人工客服获取帮助。
```

**兜底话术仍然出现**。同时，服务 stdout 中**没有出现**新增的"重排索引全部无效"告警。

这意味着：

1. **重排全部越界不是本次症状的原因**（否则新告警应该出现）；
2. 但也不能据此排除重排环节——日志中 grep 中文关键字在 Windows 控制台编码下**不可靠**（本次排查中已多次遇到中文匹配失败），需要改用 ASCII 标记或直接读日志文件字节才能确认。

**因此这个矛盾仍然敞开：单独跑四步正常，接进图之后拿不到检索结果，而定位手段（中文日志匹配）本身不可靠。**

### 已排除的假设（本轮追加的实验）

| 假设 | 实验 | 结论 |
|---|---|---|
| 重排全部越界导致空结果 | 修复后重跑真实请求，新增告警**未出现** | **排除**（且新告警本身依赖中文日志匹配，可靠性存疑） |
| `MeteredLLM` 包装破坏了 RAG 节点 | 分别用**裸 `ChatOpenAI`** 与 **`MeteredLLM`** 单独跑 `KnowledgeRAGAgent.process()` | **两者都返回正确回答，均排除** |
| 线上索引为空 | 该次真实运行的启动日志：`{'rebuilt': False, 'documents': 3, 'sources': 3}` | **排除**，索引确实有 3 篇 |

至此：**同样的查询、同样的索引、同样的模型（含包装），在进程内直接调用 RAG 节点能拿到正确回答，而经由 HTTP 运行图却拿到兜底话术。** 差异只剩下"运行环境"本身（图状态、检查点、并发闸门、事件循环），尚未找到具体原因。

### 建议的下一步排查手段（尚未执行）

1. 在 `knowledge_rag.process()` 中把 `len(raw_docs)` / `len(reranked_docs)` 以 **ASCII 前缀**写入日志（如 `RAG_DEBUG raw=2 reranked=1`），**绕开中文日志匹配不可靠的问题**；
2. 直接对运行中的服务用 `graph.astream(stream_mode="updates")` 取出 `knowledge_rag` 节点的返回增量，看 `sub_results["knowledge_rag"]` 是兜底话术还是正常回答，从而区分"检索为空"与"生成阶段异常"；
3. 复现时记录该次请求的 `messages`（尤其 `messages[-1].content` 是否真的是用户问题），排查是否因为图状态或检查点里取到了非预期的消息。

### 其他

- 本次未改动检索与生成逻辑，只增加了重排的兜底与日志。
- 该缺陷的存在说明**重排步骤长期缺乏健壮性验证**，建议后续为整个 RAG 四段式补齐异常路径用例。
