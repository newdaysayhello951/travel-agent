# 清理死代码与状态冗余

改造计划阶段 0 的第 1 步：让代码结构与文档描述一致，消除"写了但从未执行"的部分。

## 修改内容

### 1. 删除未挂载的死代码

- 删除 `python-impl/agents/intent_router.py`（122 行）。该模块实现了完整的多级意图识别，但 `create_supervisor_graph()` 只实例化它、从未 `add_node`，运行时编译出的图里没有这个节点，属于完全不会执行的代码。
- 同步删除 `python-impl/agents/__init__.py` 中的 `IntentRouterAgent` 导入与导出。
- 同步删除 `supervisor.py` 中的 `from agents.intent_router import IntentRouterAgent` 与 `intent_router = IntentRouterAgent(llm)`。

### 2. 重写 `python-impl/agents/supervisor.py`

- 删除从未被调用的 `should_check_compliance()` 函数。
- 条件边收敛：原先声明了 `knowledge_rag`、`ticket_handler`、`compliance_check` 三个去向，但 `route_decision()` 会把意图强制限定为前两个，第三个分支不可达。现改为只声明两个合法去向。
- `route_to_agent()` 简化为按意图直接返回节点名，去掉与键值同名的冗余映射表。
- 删除 `create_supervisor_graph()` 的 `short_term_memory` 参数——该参数在函数体内从未被使用（短期记忆实际只服务 `/api/history` 接口，多轮上下文由检查点提供）。同步修改 `api/main.py` 的调用处。
- 所有节点返回值由 `{**state, ...}` 改为只返回增量字段。回传整个状态会让 `messages` 白跑一次追加+去重 reducer，且未变更字段被反复搬运。
- 路由输出归一化加强：模型可能返回 `**knowledge_rag**` 这类带 Markdown 标记的内容，现在先 `strip("*` \n")` 再比对白名单。
- 修正模块 docstring（原文写"检查点仅存于内存"表述尚可，但未说明图结构）与 `create_supervisor_graph` 的返回类型注解（原注解为 `StateGraph`，实际返回已编译对象）。

### 3. 节点返回值去冗余（4 个 Agent）

`supervisor`、`knowledge_rag`、`ticket_handler`、`compliance_checker` 的节点方法一律不再回传 `**state`。

`sub_results` 字段**故意不加 reducer**：加了之后，`initial_state` 传入的空字典会与检查点里的旧值合并，导致上一轮的中间结果串进本轮，变成脏数据。当前图是串行流水线，保持默认覆盖语义更安全；等引入并行节点时，再配合显式重置或 `RemoveMessage` 一起改。因此各节点仍需要手动合并 `sub_results`，这一点已在代码注释中写明原因。

### 4. 消除原地修改图状态

`compliance_checker.process()` 原先直接对 `state["sub_results"]` 里的字典赋值。现改为复制一份再修改，避免污染检查点中已保存的状态。

### 5. 工单状态机从"定义了但不可用"变为可用

- `TicketStatus` 由 6 个状态收敛为 4 个真实状态：`created`、`processing`、`resolved`、`closed`（去掉 `pending_review`、`escalated`——它们需要人工审核与升级能力，当前并不具备）。
- 新增 `ALLOWED_TRANSITIONS` 流转校验表，以及 `STATUS_LABELS`、`PRIORITY_LABELS` 两处集中映射（原先散落在两个方法里重复定义）。
- `update_status()` 改为返回 `(工单, 错误原因)`，校验目标状态合法性与流转合法性；重复设置同一状态视为成功（幂等）。
- 新增 `update_ticket()` 与 `list_tickets()` 方法，`process()` 现在真正支持 `create`、`query`、`update`、`list` 四种动作。
- 顺带修复三处缺陷（原属阶段 1 计划，因本次重写同一段代码一并处理）：
  - `"ticket_id" in ticket_info` 是存在性判断，模型返回 `""` 或 `null` 时会去查空工单号；改为真值判断。
  - 模型输出解析失败时原先落进兜底分支，回复"暂不支持更新工单"，与真实原因无关；现在返回明确的"没能理解您的需求"并给出可用示例。
  - JSON 解析增强：剥离 Markdown 代码围栏、非字典结果也能兜底。

### 6. 对齐与实现不符的注释

- `knowledge_rag.py`：模块 docstring 与 `retrieve_documents()`、`process()` 中的"向量数据库""向量检索"改为本地词法匹配；`QUERY_REWRITE_PROMPT` 中同理。
- `ticket_handler.py`：模块 docstring 删除"通过 MCP 工具协议调用外部工单系统"——实际使用的是内部 `TicketStore`，MCP 工具层尚未被业务层调用。

## 修改原因

用户要求把项目从"演示 demo"改造为可投实习的项目，并确认按七阶段计划执行。阶段 0 的目标是让代码自洽：面试官打开代码时，注释与实现一致、没有不会执行的代码、没有定义了却不可用的能力。本步先处理图结构与工单模块这两个最显眼的部分。

## 验证结果

验证脚本 `修改记录` 之外的本机脚本 `.work/verify_step01.py`（用假模型替换模型调用，**未发出任何真实模型请求**），结果 `ALL PASS`：

- **图结构**：编译后节点为 `compliance_check / knowledge_rag / supervisor_route / synthesize / ticket_handler`（5 个，`intent_router` 已消失）；条件边目标只剩 `knowledge_rag`、`ticket_handler` 两个（原先第三个不可达分支已移除）。
- **端到端第一轮**（同一个 `thread_id`）：路由为 `knowledge_rag`、合规通过、最终回复正确、`messages` 为 2 条；`sub_results` 含 `knowledge_rag` 与 `compliance`。
- **端到端第二轮**：切换到工单分支后 `messages` 累加到 4 条；`sub_results` 为 `compliance` 与 `ticket_handler`，**未串入第一轮的知识问答结果**——验证了"不加 reducer、按轮重置"的行为符合预期。
- **工单状态机 9 项断言全部 PASS**：`created→processing` 成功、重复设置幂等、`processing→created` 被拒、`processing→resolved` 成功、`resolved→closed` 成功、`closed→processing` 被拒、未知状态值被拒、不存在的工单号被拒、`query_by_user` 返回正确条数。
- **分支分发 9 种输入逐一验证**：`create`、`query`、`query`+空号、`query`+null、`update` 合法、`update` 非法流转、`update` 缺工单号、`list`、`unknown`，均给出符合预期的回复。
- **不可变性**：`ticket_handler` 与 `knowledge_rag` 两个节点处理后，传入的 `sub_results` 字典均未被原地修改。
- **残留检查**：全项目无 `{**state}` 残留；无 `intent_router`、`IntentRouter`、`should_check_compliance`、`Literal`、`operator` 残留引用。
- **静态检查**：`agents`、`memory`、`tool_server`、`tracing`、`settings`、`api.main` 全部导入成功；`compileall` 通过。
- **真实启动**：用 `.venv` 启动 `run.py`，`/health`、`/`、`/api/tools`、`/docs`、`/openapi.json` 全部返回 HTTP 200；`/api/tools` 正确返回 4 个已注册工具及其 `inputSchema`。
- **过程中发现并修复的两个问题**：① 重写 `supervisor.py` 时把 `typing` 的 `Annotated` 一并删除，而 LangGraph 会用 `get_type_hints()` 求值状态注解，直接导致图无法编译，已补回；② `ticket_handler` 起初返回纯增量 `{"sub_results": {...}}`，在覆盖语义下会整体覆盖掉同一次请求里其他 Agent 的结果，已改为与 `knowledge_rag` 一致的手动合并。

- `WorkingMemory.get_history()`、`export_for_persistence()` 仍无调用点；`WorkingMemory.clear()` 与 `ShortTermMemory.clear()` 也已实现但没有调用方，计划在下一步（阶段 0 第 2 步）随会话重置接口一起接入。

- `memory/short_term.py`、`tool_server/mcp_server.py`、`tracing/otel_config.py` 中仍存在与实现不符的注释表述（如"基于 Redis 的会话级记忆""记录 Token 消耗""支持导出到 Jaeger/Zipkin/LangSmith"），安排在下一步处理。
- 配置项仍分散在 `settings.py` 与 `api/main.py` 中读取，`FAISS_INDEX_PATH` 这一与实现无关的环境变量名仍然保留，统一配置入口安排在下一步。
- MCP 工具层仍未被业务层调用，`handle_jsonrpc()` 仍没有 HTTP 入口（阶段 4）。
- `api/main.py` 底部的 `__main__` 分支仍默认绑定 `0.0.0.0`，与 `run.py` 的 `127.0.0.1` 不一致（阶段 3）。
- `.work/verify_step01.py` 是本机验证脚本，位于被忽略目录，不随本次提交入库。
