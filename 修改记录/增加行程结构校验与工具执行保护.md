# 增加行程结构校验与工具执行保护

## 修改内容与原因

- 新增 Pydantic 需求和行程模型，检查日期覆盖及顺序、三餐、费用非负、明细小计与总额一致性、天气日期范围，避免把可解析 JSON 直接当作正确行程。
- TripPlanner 支持可选 TripRequest；传入时强制检查城市、日期、预算上限及必去景点。页面已接入城市和日期，命令行保留自然语言追问及天气问答。
- 增加异步工具中间件：工具超时、瞬时网络错误有限重试、每次运行共享且隔离的工具尝试预算。错误文本不包含原始异常或密钥。
- 为生成和流式路径增加整体超时及图执行步数限制；保留取消语义。页面仅在生成结束且通过校验后保存行程，CLI 在已知失败时非零退出。
- 配置模板列出可调执行边界，启动检查范围；显式声明 Pydantic 依赖，评估脚本纳入新增源文件指纹。

## 验证

- 自动测试覆盖有效/无效行程、明细与总额、请求约束、工具重试、取消、次数上限、并行共享预算、整体超时、图步数超限和流式无效结果拒绝。
- 修改文件语法检查及 Git 空白检查通过。
- 13项自动回归测试全部通过。
- 真实北京天气案例完成，耗时9.36秒，2次模型调用，供应方上报5374 tokens。
- 真实长沙三日规划耗时88.05秒、17次模型调用、供应方上报174033 tokens；因PlanValidationError被拒绝，未当作成功结果。该次脚本未保存具体字段错误，不能推断确切违规字段；后续脚本已补充脱敏字段级校验诊断，未再次消耗模型调用重跑。

## 边界

- 严格校验失败后明确报错，尚未实现模型自动修正循环。
- 预算按每日住宿明细累加；离店日无住宿费用应填0。必去景点目前按名称精确匹配。
- 自然语言预算和偏好未自动解析为硬约束；调用方须显式传入 TripRequest。
- 天气真实性、营业时间、交通冲突及报价可靠性尚无全面程序化校验。
- 仅明确的超时/连接/OSError触发重试；业务错误、参数错误及取消不盲目重试。
- 尚未进行浏览器交互验收，也未批量跑完15条评估案例。
