# 增加合规修正循环

改造计划阶段 6：让"多 Agent"名副其实。此前合规审查是**一次性闸门**——不通过就直接拒答，整张图是一条直线，没有任何循环，"多 Agent 协作"的说法站不住脚。

## 修改内容

### 1. 新增整改节点 `python-impl/agents/revision.py`

`RevisionNode.revise()`：读出合规审查给出的**具体违规项**，连同待整改文本一起回传给模型重写，只替换 `sub_results` 里的文本结果，并把 `retry_count` 加一。

**只重写文本、不重跑检索**：检索结果本身不是违规来源，重跑一遍既慢又贵。

### 2. 图里第一次出现"环"

`compliance_check` 的条件边由固定边改为分支：

```
compliance_check --(通过)--> synthesize --> END
                 --(不通过且还有重试额度)--> revise --+
                                              ^        |
                                              +--------+   回到 compliance_check
                 --(不通过且额度用尽)--> synthesize（输出固定拒答话术）
```

这才是 Anthropic 所说的 **evaluator-optimizer** 模式：评估环节发现不通过，就让生成侧改，改完再评。

### 3. 启用了一直闲置的 `retry_count`

`AgentState` 里的 `retry_count` 字段此前**定义了从未被使用**，现在成为整改次数的真实计数，也是循环的终止条件。

### 4. 新增配置 `MAX_COMPLIANCE_RETRIES`

默认 1；`0` 表示不整改，行为与改造前一致（直接拒答）。`.env.example` 已同步。

### 5. 新增 7 个用例（`tests/test_revision.py`）

## 修改原因

用户要求按七阶段计划改造项目。阶段 6 针对的是整个项目最容易被戳穿的一点：**自称多 Agent，实际是一条直线**。加上整改循环后，系统具备了"生成 → 评估 → 修订 → 再评估"的真实多步协作结构。

## 验证结果

- **`pytest`：80 passed**（新增 7 例）。
- **图结构实测**（编译后打印节点与边）：

```
节点: compliance_check, knowledge_rag, revise, supervisor_route, synthesize, ticket_handler
compliance_check -> revise        (conditional)
compliance_check -> synthesize    (conditional)
revise           -> compliance_check          ← 回边，构成环
```

- **整改闭环实测**：让首次合规审查返回不通过，结果为
  - `revision_calls = 1`（真的调用了整改节点）
  - `retry_count = 1`
  - `compliance_passed = True`（复审通过）
  - `final_response = REVISED: 购买后 7 天内可申请退款（仅供参考，以合同条款为准）。`

  即**自动改写后放行**，而不是直接拒答。
- **终止性**：整改后仍不通过时，达到 `MAX_COMPLIANCE_RETRIES` 就拒答；断言 `revision_calls` 恰好等于额度（2 次），不会无限循环。
- **关闭整改**（`MAX_COMPLIANCE_RETRIES=0`）时 `revision_calls == 0`，行为回退到改造前。
- **提示词内容校验**：整改请求里确实带上了违规项（断言包含"违规项"与"保证收益"），否则模型不知道要改什么。
- 阶段 0～4 的五个验证脚本重跑均为 `ALL PASS`（`verify_step01.py` 中写死的节点与条件边断言已同步更新，该脚本位于被忽略目录、不入库）。
- 全部模块导入成功；`compileall` 通过；真实启动 `/health` 返回 **200**（并以 `MAX_COMPLIANCE_RETRIES=2` 启动确认配置生效）。

## 未解决的问题

- **本阶段的另外两项尚未完成**：
  - **SSE 流式输出**未实现——一次问答仍需等 5 次模型调用全部跑完才返回。
  - **README 的架构定性**未更新——文档里还没有把系统明确写成 "routing workflow + evaluator-optimizer"。
- 整改循环的**成本未被单独计量**：token 计量按模型名聚合，看不出整改多花了多少 token。
- 整改只做**一次全量重写**，没有做"只改违规句"的精细修订，可能把本来合规的表述也一起改掉。
- 整改提示词要求模型保持事实不变，但**没有校验整改后的事实是否真的没变**（当前只能靠复审再拦一道，而复审看的是合规性不是事实一致性）。
- `revise` 节点没有独立的超时与失败降级：模型调用失败会向上抛出，由接口层统一映射为 502。
- 循环是**单层**的（整改后直接回到合规审查），没有实现"整改同时参考用户原始问题"的更强模式。
- 阶段 5 遗留的 HTTP 层自动化测试缺口仍在（401/429/`/mcp` 目前只有手工验证）。
