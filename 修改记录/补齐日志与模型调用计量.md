# 补齐日志与模型调用计量

改造计划阶段 5 的**后半部分**（可观测性）。

## 修改内容

### 1. 日志初始化（修掉"INFO 静默消失"）

新增 `python-impl/logging_setup.py`：统一配置根 logger、输出格式与噪声库的级别，幂等。

**关键点：初始化必须放在 `lifespan` 里，不能放在模块导入时。** 因为 uvicorn 是在**导入 app 之后**才执行自己的 `dictConfig`，那一步会覆盖模块级添加的 handler——此前 `logger.info("知识库装载完成…")` 一直不输出正是这个原因。第一次修复时我把它放在模块级，实测**仍然不可见**，移到 `lifespan` 后才生效。

新增配置项 `LOG_LEVEL`（默认 INFO）。

### 2. 接通 per-agent 指标

此前 `trace_agent_call` 装饰器**只写 span、不记指标**，而 `AgentMetrics` 只在 `api/main.py` 里被记了一次 `chat`，导致 `/api/metrics` 的 `agent_metrics` 永远只有 `chat` 一项。

- `otel_config.py` 末尾新增全局实例 `AGENT_METRICS`，装饰器与接口层共用同一份统计；
- 装饰器重构：**即使追踪不可用也照样记录指标**（观测能力缺失不该让业务指标一起消失），并改用 `time.perf_counter()`；
- `api/main.py` 改为使用 `AGENT_METRICS`，不再自己 new 一个。

### 3. 模型调用 token 计量

新增 `python-impl/tracing/llm_metering.py`：

- `TokenUsage`：按模型标签累计 `calls / prompt_tokens / completion_tokens / total_tokens`，并给出 `__total__` 汇总；没有用量信息时**不产生计数条目**（避免出现 `calls=0` 的假记录）。
- `extract_usage()`：兼容 `usage_metadata` 与 `response_metadata.token_usage` 两种字段位置。
- `MeteredLLM`：**包装**模型客户端的代理，`ainvoke` 与 `with_structured_output` 都会记账，其余属性透传。选择代理而不是在 5 个调用点各写一遍，是为了**新增调用点时不会漏统计**，并且 Agent 代码零改动。
- `/api/metrics` 增加 `token_usage` 字段。

新增配置项 `OTEL_SAMPLE_RATIO`（默认 1.0）；小于 1 时 `init_tracer` 使用 `TraceIdRatioBased` 采样——全量上报在高流量下会淹没后端。

### 4. 新增 12 个可观测性用例

`tests/test_observability.py`：日志初始化的幂等性与级别、装饰器记录成功/失败指标、**不吞异常**、token 提取与聚合、`MeteredLLM` 的记账与透传、采样比例的取值范围校验。

## 修改原因

阶段 5 前半部分建立了测试，但可观测性仍有三个明确缺口：应用日志不可见、per-agent 指标全空、token 消耗完全没采集（而 token 直接等于成本）。这些在面试里都属于"我做了可观测性"这句话能否站住脚的关键。

## 验证结果

- **`pytest`：73 passed**（新增 12 例，全部通过）。
- 阶段 0～4 的五个验证脚本重跑均为 `ALL PASS`。
- 全部模块导入成功；`compileall` 通过。
- **真实启动验证**：应用侧日志已可见，stdout 中确认输出
  - `WARNING [api.main] 接口未启用鉴权（AUTH_ENABLED=True，已配置密钥=False）…`
  - `INFO [api.main] 知识库装载完成: {'rebuilt': False, 'documents': 3, 'sources': 3}`
  
  后者顺带在**真实服务**里确认了知识库索引复用生效（`rebuilt: False`）。
- **`/api/metrics` 真实返回**：`{"agent_metrics":{},"token_usage":{"__total__":{"calls":0,...}},"tool_call_log":[]}`——结构符合预期（此时尚未发生请求，故为空）。

### 测试抓到的实现缺陷（已修）

`_MeteredStructured` 最初把用量记到了**全局** `TOKEN_USAGE`，忽略了 `MeteredLLM` 注入的收集器实例，导致"结构化输出路径不记账"，而单看 `ainvoke` 路径是正常的。这个缺陷由我新写的用例断言发现（期望 `calls==2` 实际为 1），已改为把收集器实例透传下去。

## 未解决的问题

- **HTTP 层的自动化测试仍未补**：401、429、`/mcp` 入口目前只有手工 curl 验证，没有 pytest 用例（难点是 `api/main.py` 在导入时就固化配置，测试内改环境变量不生效，需要引入应用工厂或依赖覆盖）。
- 一次问答要调用 5 次模型，但**计量的标签是模型名**，无法区分"路由/改写/重排/生成/审查"分别花了多少 token。要按阶段拆分需要在调用点传标签，会侵入 Agent 代码——本次选择了不侵入。
- `usage_metadata` 是否被网关返回**取决于供应商实现**；若网关不返回用量，计量会静默为空（`__total__.calls` 为 0），没有告警。
- 追踪默认仍导出到控制台（未配置 OTLP 时），生产需要显式配置 `OTEL_EXPORTER_OTLP_ENDPOINT` 与采样率。
- `langchain_openai` 自身在 INFO 级别会打印代理探测日志，目前未压制（不影响功能，但会污染日志）。
- `.work/` 下的六个验证脚本与 pytest 套件两套验证并存，尚未统一。
