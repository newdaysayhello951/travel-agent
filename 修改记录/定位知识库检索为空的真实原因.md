# 定位知识库检索为空的真实原因

前一阶段记录了一个"矛盾"：同一个查询、同一份索引、同一个模型，进程内直接调用 RAG 节点能拿到正确回答，经由 HTTP 跑图却返回"知识库中暂未找到相关信息"。本次把它定位清楚了。

## 结论：不是应用缺陷，是我的验证脚本破坏了请求体

排查证据（服务端新增的纯 ASCII 日志 `RAG_DEBUG`）：

| 请求体来源 | 日志中的 `last_msg` | `raw`（检索命中数） | 最终回复 |
|---|---|---|---|
| PowerShell `Set-Content -Encoding ascii` | `'?????????????'` | **0** | 兜底话术"暂未找到相关信息" |
| 正确 UTF-8 字节 | `'购买后几天内可以申请退款？'` | **2** | 正确答案并带 `来源：refund_policy.md` |

**根因**：我用 `Set-Content -Encoding ascii`（以及管道拼接）构造 curl 请求体时，**中文被替换成 `?`**。服务端收到的查询是一串问号，词法检索切不出任何词元（`_terms()` 对 `?` 既不匹配 `[a-z0-9]+` 也不匹配 `[\u4e00-\u9fff]+`），于是 `search()` 直接返回空列表，`generate_answer()` 走到"无检索结果"分支输出兜底话术。

**应用侧链路完全正常**——这也解释了为什么单独跑 RAG 四步始终是对的。

这意味着**阶段 6 记录的"检索为空"、以及本次排查的起点，都是同一个验证方法问题**，不是产品缺陷。前一轮为此记录的"根因未定位"现已闭合。

## 修改内容

1. **定位手段**：在 `knowledge_rag.process()` 中增加一行纯 ASCII 的 `RAG_DEBUG` 日志（记录查询长度、改写长度、检索命中数、重排命中数、原始消息片段）。中文关键字在 Windows 控制台编码下 grep 不可靠，这是本次排查中被反复误导的原因之一；ASCII 标记一次性给出了答案。默认级别为 `DEBUG`，排查检索问题时可把 `LOG_LEVEL` 设为 `DEBUG`。
2. **保留上一轮的独立修复**：`rerank_documents()` 在"模型返回的索引全部越界"时不再静默返回空列表，而是回退到检索顺序并记日志。这个缺陷与本次症状无关，但它是真实存在的静默失败（Python 中 `-1` 等负索引还是合法下标，会静默取到末尾文档），已由 7 个用例覆盖。

## 修改原因

用户要求按七阶段计划改造项目。前一阶段遗留了一个未定位的矛盾，我承诺优先排查。现在定位完成，需要把结论、证据与排查手段记入文档，避免以后再被同一类问题误导。

## 验证结果

- **正确 UTF-8 请求体**下真实问答通过：`intent=knowledge_rag`、`compliance=True`、回复为"用户在购买后**7天内**可申请无理由退款…来源：refund_policy.md"。
- **日志对照**：同一查询在 ASCII 破坏的请求体下 `raw=0`，在 UTF-8 请求体下 `raw=2 reranked=1`，`last_msg` 亦正确显示为中文。两行日志直接锁定了差异来源。
- `pytest`：87 passed（本次未新增用例，`test_rag.py` 的 7 个用例仍全部通过）。
- 全部模块导入成功；`compileall` 通过。

## 未解决的问题

### 这次排查暴露的方法论问题（比缺陷本身更值得记）

1. **验证工具本身会成为缺陷来源**：我用 PowerShell 构造含中文的请求体，`-Encoding ascii` 与管道拼接都会破坏内容，导致"同一个请求在进程内正常、经 HTTP 失败"的假象，并让我连续两轮去怀疑应用代码。**排查"应用行为异常"之前，应先确认输入在传输链路中没有被破坏。**
2. **中文在 Windows 控制台下有多个不可靠点**：`Set-Content -Encoding ascii` 破坏内容、日志文件里中文 grep 匹配失败、`curl -d` 内联传中文易被 shell 改写。后续所有含中文的请求体一律**用编辑工具写成 UTF-8 文件 + `--data-binary @文件`**，日志排查一律**用 ASCII 标记**。
3. 我在记录里曾断言"新增告警未出现，因此排除重排越界"，这个判断本身建立在**不可靠的中文日志匹配**之上——**基于不可靠证据得出的排除结论也是不可靠的**，这一点已在上一轮记录中同步说明。
