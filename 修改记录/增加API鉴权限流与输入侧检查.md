# 增加API鉴权限流与输入侧检查

改造计划阶段 3：安全与限额。补上"没有鉴权、限流靠全局串行、只审输出不审输入"这三块短板。

## 修改内容

### 1. 新增安全层 `python-impl/security/`

- `auth.py`：API Key 鉴权。支持 `Authorization: Bearer <key>` 与 `X-API-Key: <key>` 两种携带方式；用 `secrets.compare_digest` 逐个常时比较，避免通过响应时间区分密钥前缀；调用方标识用 `sha256(key)[:12]` 派生，**不把密钥明文写进日志或限流键**。
- `ratelimit.py`：令牌桶限流器，按调用方分桶，桶数量有上限（默认 5000）以防海量 key 撑爆内存；被限流时返回建议等待秒数。
- `concurrency.py`：`KeyedConcurrencyGate`，按调用方分桶的并发信号量，取代原先的全局闸门。
- `input_guard.py`：输入侧检查，覆盖空输入、超长输入与提示注入/越权指令（试图覆盖系统指令、套取系统提示词、切换角色、绕过合规审查）。

### 2. 鉴权策略：本机可用、对外强制

在 `Settings` 上增加派生判断，避免"默认无鉴权"这种含糊状态：

| 场景 | 行为 |
|---|---|
| 配置了 `API_KEYS` | **强制校验**，业务接口缺密钥一律 401 |
| 未配置 `API_KEYS` 且 `HOST` 为本机地址 | 放行（保证本机演示可用），**启动时打印警告** |
| 未配置 `API_KEYS` 且 `HOST` 为非本机地址 | **启动直接失败**，提示"接口将对外裸奔" |

### 3. 拆掉全局 `asyncio.Semaphore(1)`

原先的全局闸门把整个服务的吞吐锁成串行，并发 100 时排队请求必然超时。改为 `KeyedConcurrencyGate`：**单个调用方仍受并发上限保护**（防止单个调用方打爆上游模型网关的额度），**不同调用方之间不再互相拖累**。

### 4. 限流顺序：先限流，后校验输入

`/api/chat` 的检查顺序是 **鉴权 → 限流 → 输入侧检查 → 并发闸门 → 图执行**。限流放在输入校验之前是**有意为之**：否则攻击者可以用大量无效请求绕过限流、持续占用服务资源。代价是**被拒绝的请求也会消耗令牌**（已在下方记录）。

### 5. 输入侧检查补齐输出侧缺口

原先合规审查只覆盖模型输出，恶意/越权输入不会被拦截。现在 `/api/chat` 在调用模型**之前**先做确定性检查（不消耗模型调用），拦不住的复杂情形仍由输出侧合规审查兜底。

### 6. 前端支持 API Key

`web/index.html` 增加密钥处理：从 `localStorage` 或 `?key=` 读取，随请求发送 `Authorization` 头；未带密钥收到 401 时弹窗提示输入并保存。本机无鉴权模式下行为不变。

### 7. 配置与依赖

新增 `API_KEYS`、`AUTH_ENABLED`、`RATE_LIMIT_PER_MINUTE`、`RATE_LIMIT_BURST`、`MAX_CONCURRENT_PER_KEY`、`INPUT_MAX_CHARS`；移除已废弃的 `MAX_CONCURRENT_REQUESTS`。`.env.example` 增加独立的"安全"分组并说明三种鉴权场景。

## 修改原因

用户要求按七阶段计划改造项目。阶段 3 解决的是"能上线吗"这个问题里最硬的短板：此前所有接口裸奔、任何人都能清空会话、一次问答要烧 5 次模型调用却没有任何限流，且并发被全局锁成串行。

## 验证结果

### 单元验证（`.work/verify_step3.py`，不发真实模型请求）— `ALL PASS`

- **配置派生判断**：本机+无密钥 → 不强制鉴权且无启动阻塞；`0.0.0.0`+无密钥 → 返回 1 条启动阻塞项（"监听非本机地址时必须配置 API_KEYS"）；对外+有密钥 → 不阻塞且强制鉴权；密钥列表能正确切分并去空（`'k1, k2 ,'` → `['k1','k2']`）；`AUTH_ENABLED=false` 时不强制。
- **调用方标识**：标识中不含密钥原文，同一密钥标识稳定。
- **令牌桶**：桶容量 3、速率 1/秒时连续 5 次结果为 `[True, True, True, False, False]`；被限流时给出等待秒数（1.00s）；不同调用方互不影响；等待 1.1 秒后令牌恢复；桶数量受 `max_buckets` 限制（写入 4 个 key 只保留 2 个桶）。
- **并发闸门**：两个不同调用方各占用 0.30 秒，总耗时 **0.30 秒**且执行顺序为 `k1-in, k2-in, k1-out, k2-out`——**证明未被全局串行化**；同一调用方两次各 0.20 秒、总耗时 0.42 秒——**证明单个调用方仍受限**；用完后并发位归零。
- **输入侧检查**：正常问题放行；空输入、超长输入（3000 字，上限 2000）、中英文提示注入、套取系统提示词、切换角色越权、绕过合规审查共 6 类均被拒绝并给出原因。

### HTTP 真实验证（服务带 `API_KEYS` 启动）

| 请求 | 结果 |
|---|---|
| `GET /health`（无需密钥） | **200** |
| `POST /api/chat` 不带密钥 | **401** `{"detail":"缺少 API Key"}` |
| `POST /api/chat` 密钥错误 | **401** `{"detail":"API Key 无效"}` |
| `GET /api/tools` 不带密钥 | **401** |
| `DELETE /api/history/x` 不带密钥 | **401** |
| 带正确密钥 + 提示注入 payload | **400** `{"detail":"输入未通过检查：试图覆盖系统指令"}`（**未调用模型**） |
| 带正确密钥 + 正常问题 | **200**，10.5 秒，返回退款政策并带 `refund_policy.md` 来源 |
| 同一密钥再一次（`per_minute=1, burst=1`） | **429**，响应头 `retry-after: 50`，体 `{"detail":"请求过于频繁，请稍后再试"}` |

### 回归与静态检查

- 阶段 0/1/2 的四个验证脚本重跑均为 `ALL PASS`（`verify_step02.py` 中读取已改名配置项的那行做了同步修正）。
- `agents`、`memory`、`tool_server`、`tracing`、`settings`、`config`、`domain`、`persistence`、`security`、`api.main` 全部导入成功；`compileall` 通过。
- **全局信号量已移除**：检索 `request_gate`、`Semaphore(1)`、`max_concurrent_requests` 仅剩两处注释中的历史说明，无代码引用。
- **前端语法**：用 Python 以 UTF-8 提取页面 `<script>` 后 `node --check` 通过（首次用 PowerShell 提取时中文被破坏导致误报，已换方式复验）。

## 未解决的问题

- 限流器与并发闸门都是**进程内实现**，多实例部署时各实例独立计数，需要换成 Redis 实现（接口已隔离，替换不影响调用方）。
- **被拒绝的请求也会消耗限流令牌**（限流先于输入校验）。这是有意的安全取舍，但会让"发错请求"的用户更快触顶；若更看重体验，可考虑把输入校验前移。
- 输入侧检查是**正则启发式**，只能拦住典型注入，绕过方式很多，本质上是第一道防线，不能替代输出侧审查与模型自身对齐。
- 密钥存放在 `.env` 明文与浏览器 `localStorage`，**没有加密存储、没有密钥轮换、没有审计日志**；本机演示可接受，公网部署应改为服务端会话 + HTTPS。
- 未实现 OAuth2 流程，仅在 401 时返回 `WWW-Authenticate: Bearer`。
- 未做 TLS/HTTPS、未接入 WAF 或反向代理层的连接数限制（属部署层）。
- 本次为验证消耗了 **1 次真实模型调用**（200 那条）；其余分支（401/400/429）在调用模型前即被拦下。
