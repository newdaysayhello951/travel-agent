# 修复路由健壮性与无界增长的缓存

改造计划阶段 1：修掉剩余的会导致"看起来能跑、实际会出问题"的真实缺陷。

## 修改内容

### 1. 路由改用结构化输出（并修掉一个只有在真实调用时才会暴露的坑）

- 新增 `RouteDecision` 模型，用 `Literal["knowledge_rag", "ticket_handler"]` 约束意图取值，交由框架保证枚举合法，替代原先"自由文本 + 白名单兜底"的做法。
- 保留文本回退路径 `_extract_intent()`：用正则从自由文本中抽取合法意图（容忍 `**knowledge_rag**` 这类 Markdown 标记和整句话），抽取不到则落到默认意图。回退时记录警告日志。
- **关键修复**：`with_structured_output()` 的默认实现走 `response_format`（json_schema），而本机实测的模型网关会以 400 拒绝（要求 messages 里出现 "json" 字样）。必须显式传 `method="function_calling"` 才能工作，该方式已实测可用。为此新增配置项 `LLM_STRUCTURED_METHOD`（默认 `function_calling`）。
- 这个坑**在假模型与静态检查下都不会暴露**：第一次真实端到端运行时，日志打出"结构化路由调用失败，回退到文本解析"，说明结构化路径实际从未生效。修复后重测，回退告警消失。

### 2. 上下文窗口：消息历史有界

此前路由判断会把**全部历史消息**塞进 prompt，而且图检查点里的 `messages` 只增不减，导致 token 成本随对话轮数线性增长，最终会撞上模型上下文上限。

- 新增配置项 `MAX_CONTEXT_MESSAGES`（默认 20）。
- `route_decision()` 只取窗口内最近若干条消息构造路由 prompt。
- `synthesize_response()` 用 `RemoveMessage` 把超出窗口的旧消息**从检查点中移除**，让状态本身不膨胀。
- 裁剪**按偶数条**执行，保证剩下的历史仍是完整的「用户提问 + 助手回答」成对结构，不会留下孤立的回答。
- 移除了 `memory/short_term.py` 中那个作用在错误数据源上的 `get_context_window()`（阶段 0 已删），改为在这里处理真正发给模型的内容。

### 3. 短期记忆内存降级：容量与过期都有界

原先内存降级路径只有条数上限，**没有过期时间、也没有会话数上限**，会话一多内存就持续增长；而且降级是静默的，Redis 真的不可用时无法从外部察觉。

- `_fallback_store` 改为 `OrderedDict`，新增 `max_sessions`（配置项 `SHORT_TERM_MAX_SESSIONS`，默认 1000）做 LRU 淘汰。
- 新增按 `ttl_seconds` 的空闲过期：读写时惰性清理超时会话，读取会刷新活跃时间（等价于空闲超时）。
- 首次降级时记录一次 `logger.warning`，说明降级原因与两条路径的行为差异；新增 `degraded` 属性便于健康检查与测试断言。
- `clear()` 同时清理过期计时，避免残留。

### 4. 工具调用日志有界

`MCPToolServer._call_log` 原先是普通列表、无上限，调用量大会持续占用内存。改为 `deque(maxlen=...)`，新增构造参数 `max_call_log` 与配置项 `MCP_CALL_LOG_MAX`（默认 200）。

### 5. 修复失败请求留下"半条历史"

原先在调用图**之前**就把用户消息写进短期记忆，请求失败（超时、网关异常）时会留下"有提问、无回复"的半条记录，与图检查点里的状态对不上。改为**图执行成功后再一起写入用户消息与助手回复**。

## 修改原因

用户要求按七阶段计划把项目改造成可投实习的项目。阶段 0 解决了结构与文档一致性，阶段 1 处理功能层面的真实缺陷：会让成本失控的无界增长、会让运维无法察觉的静默降级、以及数据不一致的历史记录。

## 验证结果

### 假模型验证（`.work/verify_step1.py`，不发真实模型请求）— `ALL PASS`

- **结构化路由主路径**：由结构化输出决定路由为 `ticket_handler`，且**不再调用文本模型**（`text_calls=0`）。
- **文本回退路径**：模拟结构化调用失败，能回退到文本解析并正确去掉 Markdown 标记得到 `knowledge_rag`；无法解析时落到默认意图。
- **上下文窗口**：窗口设为 6 时，连续 5 轮的消息条数为 `[2, 4, 6, 6, 6]`——**不裁剪会增长到 10 条**；结束时 6 条消息全部带 ID（`RemoveMessage` 的前提）；类型序列为 `Human, AI, Human, AI, Human, AI`，**成对结构保持完好**。
- **内存降级有界**：`degraded` 为 True；`max_sessions=2` 时写入 3 个会话只保留 2 个，**被淘汰的是最久未使用的那个**；人为回拨活跃时间后，超时会话在下次写入时被清理；`clear()` 同时清掉计时记录。
- **工具日志有界**：`max_call_log=3` 时调用 10 次，日志长度稳定为 3，`get_call_log()` 仍可用。

### 真实模型验证（真实调用网关）

- **探测**（3 次调用）：`function_calling` 成功返回 `Route(intent='knowledge_rag')`；`json_schema`、`json_mode` 均以 400 失败，报错为 "'messages' must contain the word 'json' in some form"。
- **第一次端到端**：`POST /api/chat` 返回 HTTP 200、耗时 22.1 秒，`intent=knowledge_rag`、合规通过、回复正确并带 `refund_policy.md` 来源；但服务日志出现"结构化路由调用失败，回退到文本解析: OpenAIInvalidRequestError"，**据此定位到 `method` 未显式指定的问题**。
- **诊断**（4 次调用）：分别用单 System、双 System、带历史、合并 System 四种 prompt 结构验证，全部以同一 400 报错失败，确认问题不在 prompt 结构而在 `response_format`。
- **修复后端到端**：
  - 第一轮 `POST /api/chat` 返回 HTTP 200、耗时 11.8 秒，`intent=knowledge_rag`、合规通过、回复正确且带来源。
  - 第二轮同一会话追问"那超过7天还能退吗？"返回 HTTP 200、耗时 10.8 秒，回复为"超过7天**可以申请退款，但需要提供合理原因**"——**正确使用了上一轮上下文**，说明检查点与多轮对话在本次改动后仍然正常。
  - **关键检查：服务日志中不再出现任何回退告警**，结构化路由已真实生效。
  - 日志中按期出现一次短期记忆降级警告，说明新增的降级可观测性在真实运行中生效。

### 其他验证

- **回归**：阶段 0 的 `.work/verify_step01.py`、`.work/verify_step02.py` 重跑均为 `ALL PASS`，本次改动未破坏图结构、工单状态机与配置层。
- **静态检查**：`agents`、`memory`、`tool_server`、`tracing`、`settings`、`config`、`api.main` 全部导入成功；`compileall` 通过。

## 未解决的问题

- 结构化路由**依赖网关支持工具调用**。不支持时会在运行期静默回退到文本解析（有警告日志，但**没有启动时探测**，也**没有对应的指标**）。本次只是把默认方式修正为实测可用的 `function_calling`，并未做能力协商。
- 上下文裁剪是**滑动窗口**：超出窗口的最早对话会被丢弃，模型会"忘记"开头内容。这是滑窗的固有代价，本次未做摘要压缩等更复杂的策略。
- 内存降级路径仍**不跨进程共享**；Redis 未安装时多实例部署会各存一份会话。
- `RemoveMessage` 的裁剪依赖消息带有 ID；若上游传入无 ID 的消息，代码会记录警告并只移除部分消息，属于**降级处理而非报错**。
- 工单仍保存在进程内存中，重启即丢（阶段 2）。
- 接口仍无鉴权与限流，新增的会话清理接口任何人都能调用（阶段 3）。
- 本次为验证消耗了真实模型调用：探测 3 次、第一次端到端约 6 次、诊断 4 次、修复后端到端约 11 次，合计约 24 次调用，均为必要的验证开销。
- `.work/verify_step1.py` 为本机验证脚本，位于被忽略目录，不随本次提交入库。
